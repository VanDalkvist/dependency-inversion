# Серия 4. Сегодня работает другой редактор
**Сезон:** «Фабрика Ани» · **уровень:** 4/4 · **наследует:** одни правила `write(post)` и `publish(post)`, независимые инструменты, составная публикация в оба канала.

## Завязка — облачный редактор пропал перед выпуском
**Аня → агент:** «Собери сегодняшний пост и опубликуй в Telegram и на сайте».
**Агент:** «Облачный редактор текста сейчас недоступен в нашей учебной ситуации. Публикацию я сделать смогу, когда будет готов пост».
Блокировка касается **одного инструмента**, а не Telegram, сайта или фабрики как целого. Не изображать реальную аварию любого существующего AI-сервиса.

## Препятствие — в фабрике зашит конкретный редактор
Аня выбирает в видимой конфигурации `CloudWriter`; до новой конструкции он вызван непосредственно внутри фабрики. Даже если рядом доступен готовый `LocalWriter`, фабрика знает только облачную реализацию.
**Аня:** «У нас есть другой редактор. Зачем менять саму фабрику, чтобы его использовать?»

## Поворот — передать готовые инструменты заранее
**Авторская реплика в диалоге агента:** «Соберём набор до запуска: выберем редактора, источники и публикаторы. Фабрика просто использует готовый набор».
**Действие зрителя:** в маленькой панели сборки заменить `Облачный редактор` на `Локальный редактор`. Обе реализации заранее соответствуют правилу `write(news) -> draft`.
**Motion:** один редактор **выходит из слота**, второй входит; сам процесс `Новости → Текст → Публикация` остаётся неподвижным. Не рисовать, будто LLM самостоятельно загрузила новый адаптер.
**Результат:** тот же процесс создаёт пост через локального редактора, затем отдельно публикует готовый документ в двух учебных каналах. Читатель видит успешный локальный прогон; внешний сервис не вызывается.

## Усложнение — разные наборы без новых фабрик
**Аня:** «Для Telegram нужен короткий пост; на сайте можно хранить полный выпуск».
Решение **не** превращается в разные функции `runTelegramFactory`, `runWebsiteFactory`. Она подаёт фабрике готовые реализации и параметры подготовки, а редактор всё так же возвращает `Draft`. Изменение содержания текста требует отдельного выбора/редактуры, его не решает DI автоматически.

**Зритель выбирает один из наборов**:
- Локальный редактор + Telegram
- Облачный редактор + Telegram + сайт (оба publisher в одном составном инструменте)
Обе конфигурации используют **одну** фабрику, а разные технические инструменты подключаются при сборке, до выполнения.

## Развязка
**Аня:** «Я меняю набор инструментов перед выпуском. Самой фабрике всё равно, какой из них я подключила, если он выполняет обещанную работу».

**Название после действия:** *внедрение зависимостей* (Dependency Injection, DI). Это **способ передать реализации**, а не синоним DIP: общие правила появились в серии 3, здесь выбираем и подаём готовые зависимости; контейнер фреймворка не требуется.

## Режиссура / проверка
Успешный прогон: (1) облачный редактор недоступен в симуляции, (2) зритель заменяет только writer, (3) фабрика выдаёт документ с `writer=local`, (4) один и тот же опубликованный текст виден в двух учебных каналах. Использовать source-owned `assembleFactory(config)` + `runFactory(ports)` из уже существующего проекта, а не fake API. Проверять, что writer заменён, а publisher не изменён; `CloudWriter` в успешном local run не вызывается.

**Финальная проверка сезона:** «Что происходит, если завтра поменяется только редактор? А если сайт снова сменит разметку? А если нужен тот же пост сразу в два канала?» — ответы по одному наблюдаемому следствию из каждой предыдущей серии, без длинной викторины.

**Мостик к следующему сезону:** «Фабрика работает. Как собрать из этих принципов другие агентские конвейеры — и не создать один гигантский инструмент?»
